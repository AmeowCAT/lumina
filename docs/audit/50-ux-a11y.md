## 2. 问题清单

### 2.1 键盘与快捷键

#### F-01 一次 Esc 可能关掉两层浮层（全局 Esc 不检查 `defaultPrevented`）

- **级别**：P2
- **位置**：`src/hooks/useKeyboardShortcuts.ts:27`；`src/components/generation/GenerationUI.tsx:974-1001`；对照依赖实现 `node_modules/@radix-ui/react-dismissable-layer/dist/index.mjs`（`if (!event.defaultPrevented && onDismiss) { event.preventDefault(); onDismiss(); }`）
- **现状**：
  ```ts
  // useKeyboardShortcuts.ts:27
  if (e.key === "Escape" && handlers.escapeActive) escRef.current();
  ```
  `handleEscape` 依次处理 放大 → 预览 → 参数面板 → 队列（`GenerationUI.tsx:979-983`），`escapeActive` 在四个浮层任一打开时为真（`GenerationUI.tsx:1000`）。
- **问题**：参数面板里有 3 个 Radix `Select`（`SamplingPanel.tsx:97,108,210`）、参数 chip 用 Radix `Popover`（`PromptDock.tsx:49-71`）。Radix 的 DismissableLayer 在 Esc 时**先**关闭自己并 `preventDefault()`，但 Lumina 的 window 监听器既不检查 `defaultPrevented`，也不区分层级，于是同一次按键继续执行 `handleEscape` → `closeSheet()`。用户体验：在步数下拉里按 Esc 想"取消选择"，面板整体消失，滚动位置与展开状态也一起没了（Sheet 关闭后仍是挂载的，但视觉上等于重开）。参数面板内还有多个 NumberInput 自带 Esc 语义（`NumberInput.tsx:79-83`：回退草稿并 blur），同样会连带关面板。
- **上游/对照依据**：上游 web UI 没有 Esc 层级概念（只有 lightbox 一个浮层，`App.vue:976-979` 用按钮关闭），因此这是 Lumina 自己引入的复杂度；同类做法是"最上层 modal 消费 keydown 后 stopPropagation，或全局层检查 `defaultPrevented`"。
- **建议**（最小改动，2 个文件）：
  1. `useKeyboardShortcuts.ts:27` 改为 `if (e.key === "Escape" && !e.defaultPrevented && handlers.escapeActive)`；
  2. `NumberInput.tsx:79` 的 Esc 分支补 `event.stopPropagation()`（或 `preventDefault()`）。
     若希望再稳一层，可把 `handleEscape` 改成"只关最上层"，并把 `escapeActive` 换成 `topLayer` 枚举。

#### F-02 快捷键用 `e.key` + 只认 `ctrlKey`：非美式键盘/大写锁定时 `Ctrl+R` 直通 WebView 刷新

- **级别**：P2
- **位置**：`src/hooks/useKeyboardShortcuts.ts:19-26`；README 键位表 `README.md:71-80`
- **现状**：
  ```ts
  if (e.ctrlKey && e.key === "r" && !e.shiftKey) {
    e.preventDefault();
    seedRef.current();
  }
  ```
- **问题**：
  1. `e.key` 受键盘布局与 Shift/CapsLock 影响：CapsLock 打开时是 `"R"`，俄语/希腊语布局下是 `"к"`/`"ρ"`。这些情况下 `preventDefault()` 不会执行，而 Tauri 2 的 WebView2 **默认启用浏览器加速键**，`Ctrl+R` 会真的刷新页面。README 明确"生成结果只在内存里"（`README.md:113`），刷新 = 静默丢掉整批未保存结果。
  2. 同理 `Ctrl+Enter`（`useKeyboardShortcuts.ts:19`）在 Mac 上要按 Cmd，但代码只认 `ctrlKey`；而 `Ctrl+,` 的处理器认了 `metaKey`（`GenerationUI.tsx:963`）——同一个 hook 文件里两种口径。
  3. 没有 `e.repeat` 过滤：按住 `Ctrl+Enter` 会连续触发，靠 `submittingRef` 同步锁兜底（`GenerationUI.tsx:123,354`），能挡住重复提交，但每个 repeat 事件都会跑一次 `prefix` 检查逻辑。
- **上游/对照依据**：`ParamsSheet.tsx:54` 写的是 `⌘,` 键帽，`Dashboard.tsx:809-816` 写 `Ctrl + Enter` / `Ctrl + ,`，`PromptDock.tsx:116` 的 placeholder 写 `Ctrl + Enter`——三处文案三种口径，实现又是第三种。
- **建议**：改用 `e.code`（`KeyR` / `Enter` / `Comma`）+ `(e.ctrlKey || e.metaKey)`；对 `Ctrl+R` 再补一个 `if (e.repeat) return`；把 `⌘` 键帽改成按平台显示（`navigator.platform` / `userAgent` 判断，或统一写成 `Ctrl/⌘`）。这样即使 `preventDefault` 因布局失效，也不会把"刷新丢结果"作为唯一后果——顺带建议在 Tauri 侧禁用 `Ctrl+R/Ctrl+Shift+R` 的浏览器加速键（跨组，见第 6 节）。

#### F-03 浮层打开时后台快捷键没有门禁

- **级别**：P2
- **位置**：`src/hooks/useKeyboardShortcuts.ts:19-26`（无浮层判断）；`GenerationUI.tsx:142-143,356,571`（只有放大对话框设了 `upscaleOpenRef`）
- **现状**：`handleGenerate` 里唯一的模态门禁是 `if (upscaleOpenRef.current) return;`（`GenerationUI.tsx:356`），`randomSeed` 也是（`:571`）；`useKeyboardShortcuts` 只在 Esc 上区分 `escapeActive`。
- **问题**：Lightbox 全屏预览打开时（点开结果图放大看），按 `Ctrl+Enter` 会向 `sd-server` 提交一次真实生成；按 `Ctrl+R` 会打开随机种子开关。用户在预览态是想"看/导航/保存"，误触一次就是几分钟 GPU 时间；而预览层完全没有反馈（结果提交后面板会被压到 Lightbox 之下）。参数面板打开时 `Ctrl+Enter` 提交是合理的（用户可能就想提交），但 Lightbox 与队列抽屉没有这个理由。
- **上游/对照依据**：上游 web UI 无键盘提交，不存在该问题；同类桌面客户端（如 A1111 的前端）通常把"提交"绑定在表单焦点内，而不是 window。
- **建议**：给 `useKeyboardShortcuts` 增加 `interactiveLayer: "none" | "lightbox" | "queue" | "sheet" | "upscale"`，`Ctrl+Enter`/`Ctrl+R` 仅在 `none | sheet` 时生效；或把 `escapeActive` 升级成 `modalActive` 并复用到这两个分支。测试里已有"放大对话框期间不提交"的用例（`GenerationUpscale.test.tsx:104-128`），把它扩到 Lightbox 即可。

#### F-06 参数面板 / 队列抽屉缺 `aria-modal`，背景无 `inert`；与放大对话框不一致

- **级别**：P2
- **位置**：`src/components/generation/ParamsSheet.tsx:39-51`（`role="dialog" aria-label="生成参数"`，无 `aria-modal`）；`src/components/generation/QueueDrawer.tsx:32-45`（`role="dialog" aria-label="任务队列"`）；对照 `UpscaleDialog.tsx:102-111`（`role="dialog" aria-modal="true"` + `GenerationUI.tsx:560-566` 给 `.app-view` 设 `inert`）与 `Lightbox.tsx:259-261`（有 `aria-modal`）
- **现状**：三个浮层三种做法：放大对话框 = aria-modal + inert；Lightbox = aria-modal，无 inert；参数面板/抽屉 = 只有 role。
- **问题**：键盘用户被 `useFocusTrap` 圈住了（`useFocusTrap.ts:31-62`），但**读屏用户**的虚拟光标不受 Tab 圈限制，可以读到、甚至激活被浮层盖住的按钮（"关闭参数面板"读完后还能继续读到"生成"按钮）。视障用户在没有 `aria-modal` 的情况下无法判断当前处于模态。
- **建议**：`ParamsSheet` / `QueueDrawer` 加 `aria-modal="true"`；把 `GenerationUI.tsx:560-566` 的 inert 逻辑抽成 `useInertBackground(active)`，四个浮层统一用（Lightbox 打开时也同样必须 inert，否则它比 Sheet 更需要）。注意 `ParamsSheet` 关闭后仍挂载，inert 要在 `open=false` 时移除，`useFocusTrap(active)` 的模式可直接复用。

#### F-07 折叠面板里的控件仍在 Tab 序

- **级别**：P2
- **位置**：`src/components/ui/Panel.tsx:59-69`
- **现状**：
  ```tsx
  <motion.div id={bodyId} animate={{ height: c ? 0 : "auto", opacity: c ? 0 : 1 }} style={{ overflow: "hidden" }}>
  ```
  折叠时只是把高度动画到 0，子树保持挂载且无 `hidden`/`inert`/`visibility`。
- **问题**：参数面板默认折叠的「高级采样」「图像输入几何」「模型使用提示」里仍有一整串 input/select/slider。键盘用户在面板里 Tab 时会进入这些 0 高度区域：焦点环被 `overflow:hidden` 裁掉、屏幕朗读器读到一堆看不见的控件，且看不出自己在哪。这与作者在 `ParamsSheet.tsx:6-12` 的注释"用 visibility 隐藏平移出画布的控件（Tab 不会掉进看不见的表单）"的意图矛盾——Sheet 整体做了，内部折叠面板没做。
- **建议**：`Panel.tsx` 在 `c === true` 时给内容容器加 `inert`（或用 `visibility: hidden` + `transition` 延迟，与 Sheet 同款写法）。React 18 支持 `inert` 属性（`inert={c || undefined}`）。

#### F-08 历史画廊虚拟滚动下，屏外条目键盘/读屏不可达

- **级别**：P2
- **位置**：`src/components/generation/HistoryGallery.tsx:78`（`VIRTUALIZE_AT = 200`）、`:440-447`（只渲染 `startIdx..endIdx`）、`:638-669`（绝对定位瓦片）
- **现状**：超过 200 个文件后只把可见范围的瓦片渲染进 DOM。
- **问题**：DOM 里不存在的瓦片自然不在 Tab 序里，也没有替代导航（无 PageDown/PgUp 处理、无 `role="grid"`/`aria-rowcount`、无"共 N 项，已显示 M 项"的播报）。键盘用户 Tab 到最后一个已渲染瓦片后，会直接跳到「刷新」按钮——后面几百张图完全无法用键盘打开。读屏同理。滚动容器 `.output-main`（`styles.css:634`）也没有 `tabindex`，键盘无法主动滚动它。
- **上游/对照依据**：A1111 的图片浏览器（image-browser 扩展）与 InvokeAI 的 gallery 都是分页/无限滚动 + 真实 DOM 元素，不存在这个盲区；Lumina 的虚拟化是为了性能（合理），但缺了键盘兜底。

## 5. 待验证假设

以下没有足够证据，只作为线索，不混入正式结论：

1. **Ctrl+R 是否真的会触发 WebView2 刷新**：取决于 Tauri 2 的 `AreBrowserAcceleratorKeysEnabled` 默认值与 WRY 的键位转发策略。代码层面的缺陷（`e.key` 精确匹配、无 `e.repeat`、只认 `ctrlKey`）是确定的；"刷新 → 丢结果"这条链路需要在真机用非美式布局/CapsLock 验证一次。
2. **Radix Select 在参数面板内按 Esc 时是否 100% 双关**：`useEscapeKeydown` 是 capture 阶段监听（`@radix-ui/react-use-escape-keydown/dist/index.mjs`），DismissableLayer 会 `preventDefault()`；但 Lumina 的 window 监听器是 bubble 阶段，两者都会跑。若某个 Radix 版本额外 `stopPropagation()`，就不会双关。**修复（检查 `defaultPrevented`）与是否双关无关，都应做**。
3. **`e.key === "r"` 在中文输入法激活时是否会变成 `Process`/`Unidentified`**：IME 组合期间的 keydown 行为在 Chromium 与 WebView2 上有差异，需实测。
4. **9.5px 文本在 125%/150% Windows 缩放下的实际像素尺寸**：Tauri 会按设备像素比缩放 CSS 像素，理论上是 11.9/14.25 物理像素，但 WebView2 的 DPI 处理与 `-webkit-font-smoothing` 组合需截图验证。
5. **上游哪些家族实际消费 `high_noise_sample_params`**：`docs/wan.md` 只证明 Wan2.2-A14B；MiniMax-H3 是否也有高噪段没有查到直接证据，所以没有把"Lumina 只对 wan-a14b 显示高噪面板"判为缺陷（反而可能是优点）。
6. **`ProgressBar` 的 ETA 在某段进度重置时是否会漂移**：`store.ts:325-330` 在 `step<=1` 或 `total` 变化时重置 `progressStartedAt`，逻辑上是对的；但只有当内核按段打印 `step X/Y` 时才成立——若内核在某些家族只打印一次 `total` 或使用不同措辞（`parseStepProgress` 只匹配 `step\s+(\d+)/(\d+)`，`store.ts:154-161`），进度与 ETA 会缺失。需要对每个家族实测一轮 stdout 格式。
7. **虚拟滚动的键盘可达性**：Chrome 在焦点位于滚动容器内且按下 PageDown 时，是否会滚动最近的可滚动祖先（`.output-main`）——若会，F-08 的严重性可降到 P3；需要真机验证。
8. **无障碍工具实测**：本报告只有静态代码 + 手算对比度，没有跑 NVDA / Accessibility Insights。aria 类结论建议由实际读屏复核一遍（尤其 F-06 / F-09）。
